# 流派数据调研：真实数据从哪来、怎么处理

> 状态：调研结论（2026-11）
> 结论先说：**不存在合法、可自动抓取的「全量流派库」**。流派内容只能走人工采集：自测 / 授权投稿 / 授权转载。
> 相关文档：[数据源清单](./数据源清单.md)（许可边界）、[数据源与采集](./数据源与采集.md)（事实数据流水线）、[数据填写指南](./数据填写指南.md)（字段）、[共享层说明](./共享层说明.md)（校验）。

---

## 一、结论摘要

| 判断 | 说明 |
|---|---|
| Wiki 有没有流派？ | **没有**。灰机 wiki 的「流派」是宝藏的标签体系（火属性/暴击/召唤…），不是玩家构筑攻略 |
| 平台能不能爬？ | **不能**。B 站/小红书/抖音/TapTap 均有登录、验证码、反爬和平台协议限制；抓取即违规 |
| 有没有现成全量库？ | 没有找到公开、可授权、结构化的全量流派数据；商业攻略站多为聚合/洗稿，不能作为来源 |
| 唯一可持续路径 | **自测 + 授权投稿 + 授权转载（人工重写为事实）** |
| 建议第一批 | 先做 **20 条自测种子** 跑通「模板 → 导入 → 校验 → 客户端显示」，再开投稿入口 |

## 三、不同数据源的处理流程

### A. 自测 / 团队实测（P0，最推荐）

```
实机游玩 → 记录构筑（武器/刻印/装备/衣服/宝藏顺序）→ 截图留存（自己的游戏画面）
→ 填 data/sources/self-test/*.json → node scripts/import-builds.js self-test <input> <output>
→ node scripts/validate-data.js <output> → 评审 → 合并进 data/builds.json
```

要点：

- 只记录**事实**（拿了什么、什么顺序、什么版本），不写「抄来的攻略原文」
- `gameVersion` 必填；版本变更后标 `待复核`
- 宝藏顺序字段 `treasureOrder` 的 `r`（稀有度）可由 wiki 宝藏目录补全
- 证据：自己的截图放 `data/sources/self-test/evidence/`（不入客户端，只做追溯）

### B. 玩家授权投稿（P0，规模化）

表单字段：

```
作者名 / 原帖链接 / 是否原创或授权（必须勾选）/ 适用版本
流派名 / 武器类型 / 刻印 / 装备与衣服 / 宝藏顺序 / 标签 / 一句话技巧
```

处理：

```
表单 → 待审队列 → 名称归一化（对照 catalog）→ import-builds.js authorized-submission
→ validate → 人工复核 → 发布
```

硬性要求：没有授权勾选 **一律不入库**；作者名 + 原帖链接必须保留；许可统一 CC BY-NC-SA 4.0。

### C. 图文社区（B 站专栏 / 小红书 / TapTap / NGA…，P1）

不抓正文，只做**人工事实卡**：

1. 人工阅读原文，记录链接、作者、发布时间
2. 只提取事实：武器、刻印、装备、衣服、宝藏及顺序、关键机制
3. 用「自己的话」写成结构化字段（不复制原句、不截原图）
4. 能联系到作者时，发授权模板（见文末）；拿到授权才可标 `authorized-submission`
5. 没授权时最多标 `maintainer`（维护者根据公开信息整理），并保留来源链接

### D. 视频（B 站 / 抖音 / YouTube）

1. 人工观看，记录关键时间点（例如 `03:42 展示毕业装`）
2. 提取画面里的装备/宝藏名称（用 catalog 校验）
3. 不下载视频、不搬运截图；需要截图时单独向作者申请
4. 来源字段写视频 URL + 时间点，方便复核

### E. Wiki（已接入，只处理事实）

- 已用 API 拉取：武器 353、装备（具体武器）353、衣服 120、刻印 27、宝藏 397、图标
- 用途：**名称/ID 对齐、宝藏深度与稀有度、图标、标签词表**
- 不产出流派内容；wiki 的「流派」是宝藏标签，不是构筑

### F. 自有游戏截图 / OCR（辅助）

- 只用自己的游戏截图（冒险笔记、结算、装备栏）
- OCR 只提取文字名称，再对照 catalog 纠正
- 不把游戏原画/UI 截图放进客户端（事实数据可以，美术表达不可以）

### G. 海外指南 / Steam / Reddit（P2）

- 人工阅读 → 翻译为事实 → 按同一模板录入
- 联系原作者授权；保留原链接与作者名

## 四、统一数据模型与规范化

所有来源最终都要落成 `data/builds.json` 的一条记录（字段见 [build.schema.json](../apps/shared/schema/build.schema.json)），关键映射：

| 外部说法 | 字段 | 归一化 |
|---|---|---|
| 武器类型 | `wt` | 映射到 THW/SHW/STAFF/DB/BOW/FD/GUN/PL/KA |
| 主刻印 | `insc` | 对照 `data/inscriptions.json` 的 id |
| 具体武器 | `gear.weapon.name` / `weaponChoices[].name` / `transition[].name` / `core[]` | 对照 `data/weapons.json` 的 items |
| 衣服 | `gear.armor.name` | 对照 `data/armors.json` |
| 宝藏 | `treasureOrder[].n` / `treasures.*` / `cursed` | 对照 `data/treasures.json`；`r` 由 wiki 深度补 |
| 标签 | `tags` | 优先用 `data/schools.json` 词表；新词先评审 |
| 来源 | `author` / `source` / `sourceType` / `license` / `gameVersion` | 必填，见 `import-builds.js` 的校验 |

来源类型只允许：`self-test` / `maintainer` / `pr` / `authorized-submission`；统一许可 `CC-BY-NC-SA-4.0`。

## 五、去重与质量审核

- **规范化键**：`wt + insc + 核心宝藏集合` 的哈希，用于精确去重
- **近似去重**：宝藏集合 Jaccard > 0.8 或装备高度重合 → 人工合并；保留别名 `aliases`
- **状态**：`draft → review → published → archived`；投诉/版本过期走 `archived`
- **可信度**：`self-test` > 带时间戳视频 > 图文贴 > 只言片语；来源里记录证据等级
- **人气/评分**：不抓平台点赞/收藏；用客户端内投票（服务端已有 ratings 模块）或作者授权数据

## 六、合规红线（必须遵守）

- 不爬 B 站/小红书/抖音/TapTap/公众号/商业攻略站
- 不搬运作者原文、截图、视频；引用只做短摘录并注明出处
- 非商用；保留作者署名与原帖链接；提供投诉下架通道
- 不使用破解/解包/内存读取的游戏资源
- 详细边界见 [数据源清单](./数据源清单.md)

| 之后 | 数据包版本化发布、过期复核、投诉下架 | 可持续运营 |
