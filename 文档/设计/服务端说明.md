## PostgreSQL 图鉴查询

先在仓库根目录生成已有 Prisma Client：

```bash
npx --no-install prisma generate --schema apps/server/prisma/schema.prisma
```

该命令只生成客户端代码，不连接数据库、不建表。不要为此运行 `db:push`、`db:migrate` 或 Prisma 数据库迁移：`catalog` schema 由 Java Flyway 管理，旧 Prisma 模型不能用于创建这套图鉴表。

- `DATABASE_URL`：PostgreSQL 连接串，适用于本地联调。
- `DATABASE_URL_FILE`：保存完整连接串的 UTF-8 文件路径，适用于挂载密钥文件的部署方式。
- 两项只能设置一项；都不设置时使用 JSON。不要将密码或连接串提交到 Git 或贴入聊天。
- 图鉴查询需要 `catalog` schema 的 USAGE，以及 `import_batch`、`active_release`、`item` 三张表的 SELECT 权限，不需要写权限或读取 `source_document`；流派和评分的增量授权见后续章节。

`GET /api/catalog` 从一次数据库查询中取得生效批次与条目，返回九类集合及内容哈希版本。保留原四类集合键，并补充武器物品、防具、灵魂石、诅咒宝藏和梦魇效果；刻印兼容 `weaponTypeId` 与 `wt`。公开 DTO 使用字段白名单并递归剥离 `t`、`depth`，不直接返回数据库完整载荷。

`GET /api/health` 在配置连接后返回 `persistence: mixed`，并用 `persistenceDetails` 分别标明各业务的存储方式。该接口是服务存活信息，不代表数据库已经可用，也不代表评分或投稿已经入库。

数据库连接失败、没有生效批次或批次条目不完整时，图鉴接口返回 HTTP 503，不悄悄回退本地 JSON。应用关闭时释放自己创建的 Prisma 连接。

## PostgreSQL 流派查询

Java 的 `V2__build_storage.sql` 新增 `game.build`、`game.build_revision` 和 `game.published_build`。先上传新 Java JAR、重建管理镜像，再使用已有命令执行 `--lc2.catalog.command=migrate`；它会沿用 catalog 中的 Flyway 历史，只追加 V2，不改写 V1 或清空已有图鉴。

在服务器给现有 Node 只读账号追加最小授权：

```bash
sudo docker compose exec -T db psql -U lc2_admin -d lc2 -v ON_ERROR_STOP=1 -c "GRANT USAGE ON SCHEMA game TO lc2_catalog_reader; GRANT SELECT ON game.published_build TO lc2_catalog_reader;"
```

Node 仅读取该已发布视图，不授予主表、历史表或写入权限。迁移和授权完成后，再部署新版 Node 镜像和 Compose 配置；无需重建已有密钥。缺表或缺权限会返回 503，不回退 JSON。

- `GET /api/builds` 支持原筛选、排序和分页；先合并当前评分再排序、分页，total 表示分页前有效数量。
- `GET /api/builds/:id` 对草稿、待审、下架和不存在记录统一返回 404。
- 详情通过共享 schema 白名单输出，并递归剥离内部 t/depth；管理侧完整载荷不直接出接口。
- 流派默认草稿；只有 Java 明确导入 PUBLISHED 状态的记录才进入玩家接口。正式流派仍为空时，列表返回 items=[]、total=0，属于正确状态。
- Java 负责流派新增、更新和状态维护；旧 Node 投稿审核入口在数据库模式下不能写流派，会返回冲突。评分已接独立数据库存储，投稿自身仍存 JSON。
- 图鉴和流派共用一个 Prisma Client，关闭服务时释放连接；健康接口仍为 mixed，但 persistenceDetails.builds 为 postgres。

## PostgreSQL 评分持久化

Java 的新增 V3__rating_storage.sql 创建 player.build_rating、player.build_rating_summary 和 player.rate_build(text,text,numeric)，继续由同一个 Flyway 迁移入口维护。先更新 Java JAR 和管理镜像并执行迁移；已有 V2 的库应新增一项迁移，不修改 V1/V2。

评分按 (build_id,voter_key) 唯一存储，同一指纹对同一流派只保留最后一次；0–10 分，允许小数和 0 分。指纹沿用服务端计算的 IP+UA 哈希前 32 位，不存 IP/UA 原文，也不作为登录账号。客户端传入的 voterKey 不参与写入。

数据库写入函数使用固定搜索路径与显式表名，锁定已发布流派、原子更新评分并计算汇总；与 Java 下架更新互斥。默认 PUBLIC 执行权已收回。同流派并发评分串行提交，写入失败或调用方事务回滚时不保留半次写入。

原只读账号仅新增 player schema 的 USAGE 及汇总视图 SELECT。评分写入使用新账号，不能沿用游戏数据只读账号或初始化管理员。在服务器执行：

```bash
sudo docker compose exec db psql -U lc2_admin -d lc2
```

在 psql 内逐条执行以下 SQL，最后通过隐藏输入设置新账号密码：

```sql
GRANT USAGE ON SCHEMA player TO lc2_catalog_reader;
GRANT SELECT ON player.build_rating_summary TO lc2_catalog_reader;
CREATE ROLE lc2_rating_writer LOGIN;
GRANT CONNECT ON DATABASE lc2 TO lc2_rating_writer;
GRANT USAGE ON SCHEMA player TO lc2_rating_writer;
GRANT EXECUTE ON FUNCTION player.rate_build(text,text,numeric) TO lc2_rating_writer;
\password lc2_rating_writer
\q
```

不授予评分账号原始评分表 SELECT/INSERT/UPDATE 或流派写权限。更新并解压新版部署包后，在部署目录生成独立写入连接：

```bash
cd ~/lc2-deploy
./scripts/ops.sh secrets --only ratings
```

输入 lc2_rating_writer 的密码。该选项只生成 `secrets/node_ratings_url`，不修改只读连接或管理令牌；更正本项配置时用 `--only ratings --replace`。Compose 通过 `RATINGS_DATABASE_URL_FILE` 挂载它。开发环境也支持 `RATINGS_DATABASE_URL`，同名环境变量和文件方式只能选一种；写入连接不能脱离只读连接单独配置。

从旧部署升级时，先执行 `./scripts/ops.sh secrets --migrate-legacy` 把 `node_database_url`、`node_ratings_database_url`、`node_submissions_database_url` 改名成统一命名，密码不需要重新输入。

启动前验证连接与权限；预检不会创建测试评分：

```bash
./scripts/ops.sh check ratings
```

预期 ok=true、ratingWrite=true，readRole 与 writeRole 分别为两个账号；正式空库 buildsWithRatings=0。失败输出的 stage 区分配置、读连接、写连接和权限核对阶段；同时保留 Prisma 初始化异常的 errorCode 与查询异常的 meta.code，不输出原始异常消息或连接串。MISSING_CONNECTION 表示连接未配，PRIVILEGE_MISMATCH 表示数据库或权限范围不符，其他安全错误码用于排查连接/缺表/授权问题。预检通过后才用 `./scripts/ops.sh up` 更新服务。

- POST /api/ratings 保留 buildId/score 请求和 buildId/avg/votes 响应；不存在、未发布或评分过程中已下架的流派返回 404。
- 列表、详情均从汇总视图计算评分与人数；不读取 ratings.json，不把流派载荷中的占位零值当作真实票数。
- 连接或权限失败返回 503，不回退 JSON；原 JSON 文件保留但不自动迁移，纯 JSON 开发模式继续可用。
- 健康信息中的 ratings 为 postgres。ratingWriteConfigured=true 只代表存在写入连接配置，实际连接与权限以部署预检为准。
- 正式流派仍为空时，不为验证接口向云端注入样例；只核对评分表数量和预检结果。正向写入、并发、回滚、下架竞态与重启验证在隔离数据库完成。

## Docker 部署（统一编排）

服务器上只有一个部署目录 `~/lc2-deploy`、一份 `compose.yaml`、一个运维入口 `scripts/ops.sh`。四个服务的差异只体现在 profile 上，不再用 `-f` 叠加多份编排文件：

| 服务 | 镜像 | 起法 |
| --- | --- | --- |
| `db` | `postgres:17` | 默认 |
| `node` | `lc2-node:<tag>`，上下文 `node-build/` | 默认 |
| `admin` | `lc2-admin:<tag>`，上下文 `admin-build/` | `profile: admin`，一次性命令 |
| `web` | `caddy:2-alpine` | `profile: web`，域名 + HTTPS |

目录约定与完整操作步骤见 [deploy/README.md](../../deploy/README.md)；这里只记录与本服务相关的部分。

Windows PowerShell 在仓库根目录生成部署包：

```powershell
Set-Location D:\Project\lost_castle_helper
npm run deploy:pack
scp out/lc2-deploy.tar.gz ubuntu@43.143.97.198:/home/ubuntu/lc2/
```

脚本产出单一压缩包 `out/lc2-deploy.tar.gz`（附 `.sha256`），解包后即为完整部署目录：`compose.yaml`、`.env.example`、`caddy/`、`scripts/`、`node-build/`、`admin-build/`、`imports/`、`data/`。包内不含桌面端、node_modules、测试、运行数据或任何密钥；不要求先提交或推送 Git。

管理端 JAR 单独上传，因为镜像只装 JAR：

```powershell
scp target\lc2-admin.jar ubuntu@43.143.97.198:/home/ubuntu/lc2/admin-build/target/
```

服务器首次部署：

```bash
mkdir -p ~/lc2-deploy && cd ~/lc2-deploy
tar -xzf lc2-deploy.tar.gz
cp .env.example .env && chmod 600 .env
./scripts/ops.sh secrets --only all          # 只读连接串 + 管理令牌
./scripts/ops.sh secrets --only ratings      # 评分写入账号
./scripts/ops.sh secrets --only submissions  # 投稿写入账号
./scripts/ops.sh up                          # db + node
./scripts/ops.sh build admin                 # 构建管理镜像
./scripts/ops.sh migrate                     # V1–V4
./scripts/ops.sh build node
./scripts/ops.sh up
```

`secrets.py` 只在当前部署目录操作：隐藏输入数据库账号密码，把经 URL 编码的连接串写入 `secrets/node_<用途>_url`，另生成随机管理令牌写入 `secrets/node_admin_token`。Compose 分别通过 `*_URL_FILE`、`ADMIN_TOKEN_FILE` 传入文件路径，不把实际内容写进镜像或 Compose 环境变量；脚本不修改数据库账号和密码。已有密钥时默认停止，维护者明确要重建时才用 `--replace`，那会使旧管理令牌失效。不要输出或上传这些密钥文件。

镜像运行时只读、以非 root 用户运行，端口只绑定服务器本机 `127.0.0.1:4317`，对外一律走 `web` 的 443；JSON 运行数据保存在独立命名卷 `lc2_node_runtime`，数据库在 `lc2_pgdata`。

启动和核对：

```bash
./scripts/ops.sh status
curl -fsS http://127.0.0.1:4317/api/health
curl -fsS http://127.0.0.1:4317/api/catalog | python3 -c 'import json,sys; c=json.load(sys.stdin)["catalog"]; print(json.dumps({"version":c["version"],"counts":{k:len(v) for k,v in c.items() if isinstance(v,list)}},ensure_ascii=False,indent=2))'
```

容器健康检查只请求 `/api/health`，判断进程能否响应，不绑定业务数据，因此空库首次部署也能正常启动；数据是否就绪看 `/api/health` 里的 `persistenceDetails`。首次图鉴基准为九类合计 1121 条，版本哈希应与 Java `status` 一致，后续数据变化以实际批次为准。

这一阶段图鉴、流派、评分和投稿均已接 PostgreSQL；数据包及限流计数等仍使用文件存储，不代表评论、收藏或全部用户业务已完成。当前阶段不要运行 `down -v`、Prisma 建表；`down -v` 会删除 `pgdata` 卷。

## 目录结构：按大功能职责划分，模块内 DDD 分层

```
apps/server/src/
├─ index.js                    启动入口（只做装配 + 启动日志）
├─ app/                        组合根（跨模块）
│  ├─ config.js                ★ 唯一读取 process.env 的地方，所有默认值集中于此
│  ├─ container.js             依赖注入：决定用哪套仓储 / 安全组件
│  ├─ http-server.js           Fastify 装配 + 按 api/routes 注册
│  ├─ admin-auth.js            鉴权（头名与口令来自配置）
│  └─ adapters.js              hash / clock 技术适配器
├─ api/                        ★ 所有接口的公共定义（唯一的地方）
│  ├─ routes.js                路由表：方法 / 路径 / 权限 / handler 名
│  ├─ handlers.js              请求处理（薄，只做参数解析 + 调用例）
│  └─ errors.js                领域错误 → HTTP 状态码
├─ shared/                     跨模块共用
│  ├─ logger.js                ★ 统一日志组件（分级别、带 scope、可 child）
│  ├─ kernel/errors.js         领域错误（含 RateLimitedError / BadRequestError）
│  ├─ kernel/event-bus.js      进程内领域事件
│  ├─ kernel/shared-kernel.js  加载前后端共用校验（@lc2/shared）
│  └─ infrastructure/json-database.js
└─ modules/                    ★ 每个目录 = 一个限界上下文
   ├─ catalog/                 图鉴：武器 / 刻印 / 宝藏 / 流派分类
   ├─ builds/                  流派聚合根 + 不变量
   ├─ submissions/             投稿与审核
   ├─ ratings/                 评分
   ├─ publishing/              数据包版本与 hash
   └─ security/                安全管控：请求指纹 + 滑动窗口限流
      └─ 每个模块内：domain/ · application/ · infrastructure/
```

**纪律**：

- 路由只在 `api/routes.js` 声明；模块里不再出现 HTTP 相关代码
- 环境变量只在 `app/config.js` 读取；业务代码不碰 `process.env`
- 日志只用 `shared/logger.js`；业务代码不直接 `console.log`
- 跨模块只能通过 application 用例或仓储接口，不 import 对方 domain 内部实现
- `domain/` 禁止出现 `fastify` / `@prisma/client` / `fs` / `crypto`

## 接口（声明于 `src/api/routes.js`）

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/health` | 公开 | 健康检查（持久化模式） |
| GET | `/api/catalog` | 公开 | 武器 9 / 刻印 27 / 流派分类 29 |
| GET | `/api/builds` | 公开 | 卡片列表（`weaponType` `inscriptionId` `sort` `limit` `offset`） |
| GET | `/api/builds/:id` | 公开 | 详情（已剥离内部字段） |
| POST | `/api/ratings` | 公开 | `{ buildId, score }`，0–10，**有限流** |
| POST | `/api/submissions` | 公开 | `{ payload, meta }`，必须勾选授权，**有限流** |
| GET | `/api/submissions` | 管理员 | 待审队列 |
| POST | `/api/submissions/:id/approve` | 管理员 | 通过 → 写回流派 |
| POST | `/api/submissions/:id/reject` | 管理员 | 驳回（必须填原因） |
| GET | `/api/packages/latest` | 公开 | 最新数据包版本 |
| POST | `/api/packages/publish` | 管理员 | 生成新数据包（sha256 + 版本递增） |

管理员鉴权：请求头名 `x-admin-token`（`API_ADMIN_HEADER` 可改），值来自 `ADMIN_TOKEN`。

## 安全管控模块（`modules/security`）

| 层 | 内容 |
|---|---|
| domain | `evaluateWindow()` 纯函数（滑动窗口）、`RateLimitPolicy` 值对象 |
| application | `RateLimiter.assert(action, key)`，超限抛 `RateLimitedError` |
| infrastructure | 请求指纹（`sha256(ip\|ua)[:32]`，不存明文）、限流计数持久化 |

**设计要点**：

1. **指纹不存明文**：只存 `sha256(ip + '|' + ua)[:32]`，换 IP 或 UA 即视为新指纹
2. **计数落盘**：写 `data/runtime/security-limits.json`，重启不能绕过限流
3. **先校验后限流**：非法请求（如分数越界）不消耗配额，避免误伤
4. **策略可配**：`RATING_RATE_LIMIT` / `SUBMISSION_RATE_LIMIT` 等环境变量控制

默认策略：

| 动作 | 默认限制 | 说明 |
|---|---|---|
| `rating` | 20 次 / 分钟 | 同指纹同窗口 |
| `submission` | 5 次 / 10 分钟 | 人工审核成本高，门槛更高 |

## 已实现的领域规则

| 规则 | 位置 |
|---|---|
| 字段级校验（与客户端同一份 `@lc2/shared`） | `modules/builds/domain/build.js` |

| 只有 `PENDING` 能被审核 | 同上 |
| 评分同指纹只保留最后一次 | `modules/ratings/domain/rating.js` |
| 限流（评分 / 投稿） | `modules/security/` |
| 数据包版本递增 + 稳定序列化（同内容同 hash） | `modules/publishing/domain/package.js` |
| 单条脏数据不拖垮列表 | `modules/builds/application/use-cases.js`（返回 `skipped`） |

## 终端乱码（Windows）

控制台默认 936(GBK)、Node 输出 UTF-8，中文日志会乱码。
`npm run start` / `npm run dev` 已内置 `chcp 65001`；若直接 `node src/index.js`，请先执行：

```powershell
chcp 65001
```
