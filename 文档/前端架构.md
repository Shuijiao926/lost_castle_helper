# 前端架构（渲染层）

> 适用对象：改客户端界面 / 加功能前想先了解「代码放哪、依赖哪个方向」的同学。
> 相关：[技术架构](./技术架构.md)（双窗口模型）、[客户端说明](./客户端说明.md)（运行与打包）、[原型说明](./原型说明.md)。

## 1. 重构前的问题

渲染层原本是一个 1669 行的 `index.html`：内联 560 行 CSS + 1015 行 JS，里面混着

- 静态数据（武器 / 刻印目录、内置示例流派）
- 业务规则（筛选 / 搜索 / 排序 / 评分星级 / 数据归一化）
- 基础设施（IPC 取数据、印象读写 localStorage / userData）
- 视图渲染、DOM 事件、键盘、Electron 双窗口适配
- 动效（靠猴补丁替换 `openDetail` / `render` 等业务函数实现）

后果：加一个功能要在大文件里多处找；业务规则改错只能靠手点验证；动效和业务互相纠缠。

## 2. 采用的分层（DDD 思想的简化版）

渲染层不是后端服务，没有聚合根 / 领域事件 / 多仓储的复杂度，所以**只取 DDD 真正有用的三点**：

1. **领域与表现分离**：业务规则写成纯函数，不碰 DOM；
2. **依赖单向**：UI → 应用 → 领域；基础设施被应用层依赖，领域不依赖任何外部；
3. **边界显式**：数据从哪来（infra）、规则是什么（domain）、看到什么（app）各归其位。

```
┌─────────────────────────────────────────────────────────────┐
│ app.js（应用 / 表现层 · 组合根）                              │
│   state、视图渲染、DOM 事件、键盘、Electron 双窗口适配          │
└───────────────┬─────────────────────────┬───────────────────┘
                │                         │
     ┌──────────▼──────────┐   ┌──────────▼──────────┐
     │ domain/builds.js    │   │ infra/repositories.js│
     │ 纯业务规则（无 DOM）  │   │ 数据源 / 本地持久化   │
     └──────────▲──────────┘   └──────────▲──────────┘
                │                         │
     ┌──────────┴──────────┐   ┌──────────┴──────────┐
     │ data/catalog.js     │   │ Electron IPC /       │
     │ 静态目录 + 示例数据   │   │ localStorage / 文件  │
     └─────────────────────┘   └─────────────────────┘
                ▲
     ┌──────────┴──────────────────────────┐
     │ ui/{icons, dom, motion}             │
     │ 图标资源 / DOM 工具 / 动效（表现）     │
     └─────────────────────────────────────┘
```

| 层 | 文件 | 职责 | 允许依赖 |
|---|---|---|---|
| 数据 | `js/data/catalog.js` | 武器 / 刻印目录、内置示例流派、标签索引 | 无 |
| 领域 | `js/domain/builds.js` | 目录查找、星级渲染、筛选 / 搜索 / 排序、DTO 归一化 | data（注入） |
| 基础设施 | `js/infra/repositories.js` | 流派数据源（IPC）、印象持久化（IPC / localStorage） | Electron / 浏览器环境（注入） |
| 表现 | `js/ui/icons.js`、`js/ui/dom.js`、`js/ui/motion.js` | 图标、DOM 引用与转义、动效节奏 | 无 |
| 应用 / 表现 | `js/app.js` | 状态、视图、交互、键盘、Electron 适配 | 以上全部（组合根） |
| 壳 | `index.html` | 只放结构 + 资源引用 | — |

依赖规则：**domain 不 import app / infra / ui；infra 不碰 DOM；ui 工具不碰业务状态。**

## 3. 目录结构

```

   ├─ domain/builds.js     # 领域规则（纯函数，可单测）
```

## 4. 关键数据流

```
main 进程 getData ──IPC──▶ infra.data.load()
                              │
                              ▼
                    domain.normalizeBuilds()   // source→src, updatedAt→updated
                              │
                              ▼
                   app.BUILDS（内置示例兜底）
                              │
        state（筛选 / 排序 / 收藏 / 评分 / 印象）
                              │
                              ▼
              domain.visibleBuilds(BUILDS, filters)   // 先排序后筛选
                              │
                              ▼
                  renderFeed() / renderDetail()
```

印象（用户评价）链路，覆盖更新、不做增量历史：

```
卡片气泡图标 → openNote() → saveNote()
                              │
                              ▼
        infra.notes.save(buildId, text, state.notes)
        ├─ Electron：lc2.notesSet → main 写 userData/notes.json
        └─ 浏览器 / 原型：localStorage['lc2.notes.v1']
```

## 5. 两个工程决策

### 5.1 为什么不用 ES Modules

渲染层是 `loadFile()` 加载的 `file://` 页面，Chromium 对 `file://` 下的模块脚本做 CORS
限制，`import` 会失败；改成自定义协议或打包器又给原型（浏览器双击打开）增加门槛。
因此采用**经典脚本 + `window.LC2` 命名空间**，按依赖顺序在 `index.html` 末尾加载：

```html
<script src="js/data/catalog.js"></script>
<script src="js/domain/builds.js"></script>
<script src="js/infra/repositories.js"></script>
<script src="js/ui/icons.js"></script>
<script src="js/ui/dom.js"></script>
<script src="js/ui/motion.js"></script>
<script src="js/app.js"></script>
```

代价是加载顺序即依赖顺序；收益是零构建、原型与客户端共用同一套代码。

### 5.2 领域 / 仓储用工厂函数（UMD）

`catalog.js` 导出数据工厂，`domain/builds.js` 与 `infra/repositories.js` 导出
`createXxx(依赖)` 工厂：

- 浏览器：脚本自己组装 `LC2.domain` / `LC2.infra`；
- Node 测试：`require()` 后注入目录 / 假 IPC / 假 localStorage。

所以领域和仓储可以在 `node --test` 里直接测，不需要启动 Electron。

## 6. 动效不再使用猴补丁

重构前动效层靠替换业务函数实现（`openDetail = function(){...}`），业务与动效互相污染。
现在由 app 在明确时机调用 `motion`：

| 时机 | 调用 |
|---|---|
| 打开详情 / 返回列表 | `motion.replay(elDetail,'m-view-in')` / `motion.replay(elFeed,'m-view-back')` |
| 展开卡片 | `motion.replay(card,'m-expanding')` |
| 收藏 | `motion.replay(el,'m-pop')` |
| 筛选确认后 | `render()` 内检测 `pendingStagger` → `motion.stagger(elFeed)` |
| 面板呼出 | 主进程 `onPanel` → `setTimeout(motion.panelIn, 16)` |
| 键盘触发按钮 | `motion.press(el)` |

## 7. 开发与测试

```powershell
# 客户端
npm run desktop

# 桌面层单测（29 用例：渲染层 11 + 主进程 18，无需 Electron）
npm run desktop:test          # 或 cd apps/desktop; node --test "test/*.test.js"

# 其他校验
node scripts/check-links.js   # 文档内链
node scripts/validate-data.js # 数据文件
cd apps/server; node --test   # 服务端
```

开发热部署：`setupDevHotReload()` 现在**递归监听整个 `renderer/` 目录**，改
`js/`、`styles/`、`index.html`、图片都会自动刷新渲染窗口（`LC2_HOT=0` 可关）。

## 9. 后续还能怎么拆（暂不做）

当前 `app.js` 仍是「应用 + 表现」合一的约 700 行，属于可接受的范围。若继续变大，按下面顺序拆：

1. `ui/views/feed.js`、`ui/views/detail.js`：把 `renderFeed` / `renderDetail` 独立；
2. `ui/views/overlays.js`：筛选 / 帮助 / 印象三个弹层；
3. `ui/input.js`：搜索、筛选、键盘路由；
4. `ui/shell.js`：Electron 双窗口适配与拖拽；
5. 需要跨视图共享状态时，再引入 `core/store.js`（state + subscribe），而不是一步到位上框架。

**不引入前端框架**：面板只有列表 / 详情两态、重渲染成本极低，引入框架收益小于构建与依赖成本。
