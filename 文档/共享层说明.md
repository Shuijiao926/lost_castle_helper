# apps/shared — 前后端共用

只做一件事：**流派数据的校验**。客户端提交前预检、服务端接收时校验，用同一份代码，避免两边规则漂移。

## 内容

| 文件 | 说明 |
|---|---|
| `validate.js` | `validateBuild(build)` / `validateFile(file)` + 枚举常量 |
| `schema/build.schema.json` | 完整 JSON Schema（给人看、给外部工具用） |

## 用法

```js
// 服务端（相对路径引用，未走 npm 包解析）
const { validateBuild } = require('../../../../apps/shared/validate');

const r = validateBuild(build);
if (!r.ok) return reply.code(422).send({ errors: r.errors });
```

```js
// 客户端（Node 侧）
const { validateFile } = require('../../../../apps/shared/validate');
```

返回结构统一：

```js
{ ok: true,  errors: [] }
{ ok: false, errors: ['name：必填，不超过 20 字', 'wt：必须是 THW/SHW/...'] }
```

## 校验范围

只做**必填 + 类型 + 取值**，不做完整 Schema 校验（那是 `build.schema.json` 的事）：

- 必填：`id` `name` `wt` `insc` `rating` `votes` `features` `tip` `author` `gameVersion`
- 枚举：武器类型、稀有度、净化判断、武器推荐标签、流派深度
- 结构：`resonance.code` 形如 `2-1-2`；`treasureOrder[].t` 只能是 S/R/1/2
- 唯一性：`validateFile` 会检查 `builds[].id` 是否重复

## 为什么不做成 npm 包

现阶段只有两个消费方、代码不到 200 行，相对路径引用最省事。
等 `apps/admin` 也接入后，再升级成 workspace 包（`dependencies: {"@lc2/shared": "workspace:*"}`）。
